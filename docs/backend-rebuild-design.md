# Questions 后端重构设计

本文描述目标系统，不代表当前代码已经具备这些能力。当前行为仍以现有 API、存储与产品文档为准；实施后再同步更新它们。

## 1. 已确认的业务边界

- 线下工作人员引导的个人答题，每场一般不超过 10 人次；没有团队共享进度、排名、匹配或高并发需求。
- 玩家只能参加管理员定向下发的场次，不按等级自动发场次，不开放自助报名。
- 场次可限制参与等级；完成后不再出现在待玩列表，管理员重新下发才能再次参加。
- 每次重新下发都是新的游玩，经验和奖品与首次参加相同；历史记录保留，不原地清空。
- 奖品主要是实物，可能由工作人员交付，也可能通过地点线索或柜子领取；必须支持管理员核销，不做发货。
- 账号用于登录且唯一；昵称用于显示和称呼，不要求唯一，不作为关联标识。
- 管理员创建玩家，玩家可改密码、昵称和头像；注册能力首版关闭。
- 不兼容旧链接、旧身份字符串和旧浏览器进度。不导入旧经验、惩罚、已读或奖品状态。
- 旧题目与关联内容保留一份本地原始导出，用来重新配置和验收，不承担旧系统兼容职责。
- 现有 PocketBase 是通过用户所述的 1Panel 容器运行二进制；实际版本、工作目录、挂载、启动命令和其他应用依赖尚待核实。

## 2. 工程选择

采用一个 PocketBase 服务，使用其认证、文件存储、SQLite 和 JavaScript 扩展。不新增 Node HTTP 服务、Redis、消息队列或微服务。浏览器只负责展示和交互，所有成绩与权益由服务端决定。

建议将服务端源码放入 `sitkin-pb-backend-management/backend/`，与该仓库的管理前端分开构建、测试和发布。玩家端仍保留在 `questions-web`。正式版本号待检查线上二进制后锁定，不把前端 SDK 版本当成服务端版本。

两个认证集合隔离玩家与管理员。普通管理页面使用业务管理员账号；PocketBase 超级管理员只用于部署、初始化和维护，不把其凭据放进前端、仓库或可下载的配置文件。

首版使用固定管理员权限，不建设可编辑 RBAC 权限系统。后续可以增加只允许现场操作的工作人员角色。

## 3. 业务规则

### 3.1 场次、分配与等级门槛

题目是可复用内容；小关卡是场次中的一项编排；场次定义题目顺序和整体演出；分配记录表示某个玩家的一次游玩。相同题目可以被多个场次使用，也可以在同一场次出现多次，各小关卡进度互不混淆。

管理员可选择指定用户或“所有有效用户”批量下发，每个用户生成独立分配记录。“所有用户”指首次提交时有效玩家的快照，不自动包含未来新建用户；重试同一请求不能扩展接收范围。已存在同系列未结束分配的用户跳过；已完成用户默认也跳过，只有明确勾选重新下发或执行重发操作才再次安排。界面提交前显示目标范围，提交后逐用户报告成功与跳过原因。

管理员给同一用户重新下发同一场次时创建新分配，并关联上次分配，便于追溯。等级不达标不影响预分配，仍在开始时检查。

默认规则：

1. 场次配置最低、最高等级，边界均包含；最高等级留空表示无上限。
2. 分配时可以给尚未达标的玩家预先安排，界面显示未满足条件，不自动开始。
3. **首次开始该次游玩时检查等级并保存入场快照**。开始后升级超出上限不会中断本场；重发后的新游玩重新检查。
4. 每次答题仍检查账号有效性、分配归属、撤回状态、开放时间、前置关卡与惩罚，不能因入场后跳过这些校验。
5. 同一用户可以有多个不同场次，按管理员设置顺序展示，但首版不强制场次之间串行。场次内默认逐题解锁。
6. 默认不允许同一用户对同一场次系列同时存在两个未结束分配。已过期但未结案的分配需取消后再发，服务端事务内检查。
7. 开始和截止时间采用 UTC 存储，管理界面显示明确时区；开始时间包含，截止时间不包含。
8. 正常中断后恢复原分配；延长截止时间、解除锁定不重新发放已结算经验或奖品。重新玩才创建新分配。

分配的持久状态为 `assigned / active / completed / cancelled`；待开放、过期、等级不符是根据时间和用户状态计算的展示状态。撤回分配阻止继续答题，但不自动扣回已经获得的经验和奖品；需要撤销权益时走独立有审计的管理操作。

### 3.2 发布与版本

为控制实现成本，首版不单独设置题目主表加题目版本表、场次主表加场次版本表。采用**版本化记录**：

- 题目、场次和叙事内容每条记录具有 `seriesKey`、`revision`、`status`。
- `seriesKey` 是稳定系列标识，`revision` 是该系列的正整数版本；两者组合唯一。
- 草稿可修改；发布后内容、答案、编排、经验和发奖规则冻结。归档只阻止新分配，不破坏旧分配的访问。
- 修改已发布内容时复制成新草稿，发布后得到新的记录 ID。场次小关卡引用具体题目版本 ID，分配引用具体场次版本 ID。
- 后台按系列组织列表并提供“创建新版本”，用户不需要手工维护版本字段。
- 对已开始游玩修正错误题目，首版采用人工通关或解锁，并记审计；不静默替换正在玩的版本。

发布操作在同一事务中检查所有引用：题目与答案有效、顺序唯一、至少一关、经验非负、奖励数量合法、线索触发目标同属本场、引用叙事已经发布、时间/等级范围有效。跨系列引用、失效引用或循环内部跳转不允许发布。

### 3.3 判题、进度与惩罚

- 首版保留填空和单选题；填空兼容现有答案标准化规则，必须在实际 PocketBase JS 运行时测试 NFKC、Unicode 空白、标点和大小写处理。
- 答案单独存储，玩家端任何接口、关联展开、实时订阅或缓存中都不能拿到未授权答案。
- 经验配置在场次小关卡上，首次成功完成该次分配的小关卡时发放一次。
- 填空默认可重复尝试且不惩罚；单选采用明确配置的递进惩罚。新后台不把永久锁定作为隐藏默认，必须显式设置。
- 惩罚用结构化的 `durationSeconds` 或 `lock` 表达，不沿用 `-1` 特殊时间值。所有截止时间来自服务端。
- 小关卡持久化完成状态、错误次数、冷却截止时间和永久锁定标记，UI 根据这些值计算待答/冷却/锁定状态。
- 后台提供解除惩罚、人工通过和撤回场次操作，必须填写原因；人工通过使用相同结算逻辑。
- 所有小关卡均完成即完成场次。首版不加入可选题、随机抽题、分支任务和复杂依赖图。

### 3.4 经验与等级

经验采用整数。`game_xp_ledger` 是事实来源，`game_player_stats.totalXp` 是同事务维护的查询汇总，不是玩家可写字段。

等级定义使用固定顺序和累计经验下限；第一级从 0 开始，下限严格递增。当前等级是总经验对应的最高达标等级，由服务端计算后与用户资料一起返回，不在多个表里维护独立可编辑的“当前等级”。

管理员可配置等级名称、素材与阈值。阈值调整先预览受影响玩家，再一次性应用并留审计；会影响尚未开始的场次资格，不会撤销已保存的入场资格。调阈值不重新发奖。被引用的等级顺序不能任意删除或重排。

手工调整经验必须填写原因并写入正负流水，调整后总经验不能小于 0；不直接改总数，不删除历史流水。跨多个等级时返回升级前后等级，前端一次展示最终等级，避免连续阻塞弹窗。

### 3.5 奖品与核销

奖品定义、发放规则、用户获得的奖品是三个不同概念。规则首版只支持完成某小关卡、完成场次两个触发点；管理员也可有原因地人工发奖。不做可编程条件引擎或等级变更自动发奖。

用户奖品状态为 `available / redeemed / voided`，发放记录保存奖品名称、说明和图片快照，避免后来编辑奖品定义导致历史奖品变义。

- 用户可看自己已获得的奖品、领取方式和核销结果，不能自己核销。
- 管理员确认交付或领取后核销，记录操作人、时间和备注；不要求对接物流或柜机 API。
- 丰巢等柜子的操作由现场人员完成，系统只保存领取说明或该份奖品的临时领取信息，不声称已对接开柜。
- 可重复使用的领取地点可存在奖品定义；取件码、一次性密码必须绑定某一次发放，不能放进共享场次模板。
- 首版支持管理员发奖后补充专属领取信息；未准备好时提示联系工作人员，不显示其他人的信息。敏感领取信息不写分析埋点、通用日志或幂等响应快照。
- 同一份发放只能成功核销一次，双击和两个管理员同时操作不得重复核销。
- 数量默认为 1；若一次发放多件，首版整笔核销，不做部分核销、仓储和库存预占。
- 误核销撤销为独立有原因的操作，保留原审计；它不会自动重置真实柜子的密码或实际物品状态。

### 3.6 线索、演出和媒体

场次拥有默认 BGM、背景、完成演出和完成后目标；小关卡可配置覆盖和自动前进。BGM 覆盖明确区分继承、指定和静音，不用空字符串同时表示多个意思。

线索关联场次及可选的小关卡，触发条件固定为入场、完成小关卡、完成场次或管理员解锁。解锁记录归属一次分配；玩家接口只返回已经解锁的内容。

Letter 与 Bless 合并为叙事内容集合中的两种有版本的类型，正文仍使用各自经过校验的结构化 JSON，保留现有渲染组件。它们通过已解锁线索或完成目标访问，旧 `from` 参数不具有授权作用。

公开装饰图片、BGM 可以继续走现有媒体来源。含答案、私人信件、取件码的素材不能仅靠隐藏 URL 保密；应迁入受保护文件或受控存储。旧内容导出只保留 URL，清理旧存储前须确认文件可用性和归属。

### 3.7 通知和运营记录

通知正文与接收记录分开。管理员发送时将目标用户展开为接收记录，支持个人、选定场次分配和当时的全部有效玩家；以后注册的玩家不会自动收到过去的广播。

已读由服务端记录，换设备可恢复。首版保留可见页面每 5 秒轮询并在恢复可见时刷新，不为不足 10 人的场景增加额外消息服务。答题运营记录直接查服务端提交表，现有包含标准答案的客户端埋点下线。

## 4. 逻辑数据字典

以下是逻辑字段，不是可直接导入的 PocketBase schema；字段类型、空值编码、索引语法以锁定版本的迁移测试为准。各表均使用 PocketBase 记录 ID 和创建/更新时间；除特殊注明，业务事实只允许服务端写。

| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------- |
| `game_players`（auth）       | `account`, `displayName`, `avatar`, `status`, `mustChangePassword`                                                                                     | 账号先规范化后唯一；昵称可重复；客户端不可改状态          |

| `game_player_stats`          | `player`, `totalXp`                                                                                                                                    | `player` 唯一；经验非负；可由流水核对                     |
| `game_level_definitions`     | `order`, `name`, `minTotalXp`, `visualConfig`                                                                                                          | 顺序和经验阈值各自唯一；应用层验证整体递增                |

| `game_session_levels`        | `session`, `question`, `position`, `xp`, `penaltyPolicy`, `autoNext`, `presentationOverride`                                                           | `(session, position)` 唯一；小关卡 ID 独立于题目 ID       |
| `game_assignments`           | `player`, `session`, `previousAssignment?`, `order`, `status`, `startsAt?`, `endsAt?`, `startedAt?`, `completedAt?`, `admissionSnapshot`, `assignedBy` | 服务端验证同系列活动分配不重复；重发一定新 ID             |

| `game_reward_rules`          | `session`, `sessionLevel?`, `trigger`, `reward`, `quantity`                                                                                            | 触发点与引用一致；随场次发布冻结                          |
| `game_player_rewards`        | `player`, `assignment?`, `rule?`, `sourceKey`, `reward`, `snapshot`, `quantity`, `status`, `claimDetails`, `redeemedAt?`, `redeemedBy?`                | `sourceKey` 唯一；奖品归属不可由客户端改写                |

| `game_clue_unlocks`          | `assignment`, `clue`, `unlockedAt`, `sourceType`, `actor?`                                                                                             | `(assignment, clue)` 唯一                                 |

| `game_notification_receipts` | `notification`, `player`, `assignment?`, `readAt?`                                                                                                     | `(notification, player)` 唯一；跨设备共享已读             |
| `game_admin_audit_logs`      | `actor`, `action`, `entityType`, `entityId`, `reason`, `safeDiff`, `requestId`                                                                         | 只追加；禁止包含密码、令牌、完整取件码                    |
| `game_command_receipts`      | `actorCollection`, `actorId`, `operation`, `requestId`, `requestHash`, `resultRefs`                                                                    | 主体+操作+请求键唯一；只存业务结果引用，不存敏感响应正文  |

这些集合不对应 22 个管理菜单。业务配置通过题库、场次、玩家、奖品等页面统一编辑；进度、流水、幂等记录和审计由系统维护。

账号初始建议限制为经过小写规范化的 3～32 位字母、数字、点、下划线和短横线，昵称 1～40 字符。头像首版建议 JPEG/PNG/WebP、单文件不超过 2 MB，同时检查文件内容和尺寸，拒绝 SVG。密码使用 PocketBase 内置散列，不自建密码表。

玩家创建、改密码、禁用等动作必须验证服务端身份。初始密码只在创建时交付，不记录明文；首次登录需要改密。忘记密码首版由管理员重置并要求再次改密，不依赖尚未配置的邮箱服务。具体会话失效机制在锁定 PocketBase 版本后验证，不能仅清理当前浏览器就声称其他设备已退出。

## 5. 权限边界

| 数据/操作                      | 未登录     | 玩家                       | 管理员                                 |
| ------------------------------ | ---------- | -------------------------- | -------------------------------------- |
| 密码登录                       | 允许，限速 | 可重新认证                 | 可重新认证                             |
| 自助注册                       | 禁止       | 禁止                       | 通过建用户命令创建玩家                 |
| 个人资料与密码                 | 禁止       | 仅本人，字段白名单         | 管理命令，敏感操作审计                 |
| 场次和当前可答题面             | 禁止       | 仅自己的分配、允许的题目   | 可预览；预览不产生真实结算             |
| 标准答案、未解锁线索           | 禁止       | 禁止                       | 授权管理界面可读                       |
| 进度、经验、奖品               | 禁止       | 只读本人                   | 可读；写入必须走业务命令               |
| 核销、人工通过、解锁、经验调整 | 禁止       | 禁止                       | 校验、事务、幂等、审计                 |
| 通知                           | 禁止       | 只读本人接收记录；可标已读 | 可发送和撤回                           |
| 审计和业务管理记录             | 禁止       | 禁止                       | 可读，不直接篡改                       |
| 建表与服务配置                 | 禁止       | 禁止                       | 普通管理员也禁止；维护用超级管理员执行 |

玩家侧除认证与受控文件接口外，优先使用 `/api/questions/v1` 自定义 DTO 接口。底层敏感内容集合对玩家锁定 CRUD；少量需要直接文件读取或本人查询的集合必须设置严格规则。不能依赖请求里的 `fields`、`filter` 或不显示按钮来保密。

所有归属判断同时检查认证集合与记录 ID，防止不同认证集合的相同 ID 被混用。自定义路由使用数据库内部 API时不会自动获得业务授权，必须复用统一的鉴权、账号状态、归属、解锁检查。文件、关联展开和实时接口同样纳入越权测试。

## 7. 原子性与重试

一次判题事务执行：查身份和归属 → 查幂等请求 → 查入场与前置条件 → 判题 → 记录提交 → 更新进度 → 追加经验流水并更新汇总 → 生成奖品和解锁记录 → 必要时完成场次 → 保存命令结果引用。

- 同一主体同一操作同一请求键重复调用，返回相同业务结果；键相同但请求内容不同则报冲突。
- 小关卡经验来源键是 `assignmentId + sessionLevelId + completion`；奖品来源键包含分配 ID 与规则 ID。重新下发得到新分配 ID，因此可再次正常获得。
- 即使客户端换一个请求键重复提交正确答案，也不能再次结算已经完成的关卡；完成后提交不会增加错误次数或施加惩罚。
- 错误答案因断网重试只计一次错误。幂等依据至少保留与对应业务历史同样长，不随意按短 TTL 删除。
- 响应丢失时前端使用原请求键重试；答案编辑后的下一次提交使用新键。刷新后可查询服务端状态，不凭本地“成功”标记发奖。
- 回放结果前重新校验当前访问权限，领取码等敏感内容从当前有权访问的记录读取，不从永久响应缓存泄露。
- 事务只做本地数据库操作，不包含邮件、外部媒体下载、柜机或其他网络请求。外部通知不作为答题成功的前置条件。
